Pause so the user can review what you changed since the last checkpoint, then continue with their decision.

OpenCode computes the exact diff since the previous checkpoint and which changed file uses which. The user sees a short summary in the terminal. A map page in the browser draws your flow as a state machine, checks each arrow against the real imports, and shows the project with your notes next to the real diff, like a short guide for someone new to this code. The user then approves, asks for a revision, or stops the run.

When to call it:
- When a feature or behavior change is complete: the program now does something new or different, such as a feature that works, changed logic or data flow, or a fixed bug. This usually covers several edits across a few files.
- Not when the program does nothing new yet: if you only added or changed docs, simple static pages, config, or styles, or renamed, reformatted, or moved code, keep working, even when the user listed that work as a separate item. Those changes show up in the next checkpoint. For example, if the user asks for a README, a simple HTML page, and a password check on the login form, call checkpoint once, after the password check works.
- On its own, after your edits have finished. Never call it in the same response as an edit.
- Only when you changed files since the last checkpoint.

Parameters shown in the terminal:
- title: a short name for the feature or change (3-8 words)
- steps: what you did since the last checkpoint, in order. One short sentence per step (under 15 words) that starts with "I", for example "I added applyDiscount() to checkout.js so totals can use a code."
- impact: one sentence on what the program now does differently

Parameters shown on the map page:
- overview: the big picture in 2-4 sentences: what this change does and why
- flow: how the program moves through your change, as a state machine: one arrow per step, in order, from the user's action to the result. Each arrow goes from one file to another (or stays in the same file) and has a short action. For example: user → src/index.js "runs the shop", src/index.js → src/checkout.js "asks receipt() for the receipt", src/checkout.js → src/cart.js "asks total() for the price", src/cart.js → src/cart.js "takes 10% off for SAVE10". Use 3-7 arrows.
- notes: one note for each file you changed: its path relative to the project, what the file is for, and what you changed in it and why
- check: how the user can try the change: a command to run or what to click, and what they should see

The result tells you what the user decided:
- Approved: continue with your plan.
- Revision requested: apply the user's feedback, then call checkpoint again before starting anything new.
